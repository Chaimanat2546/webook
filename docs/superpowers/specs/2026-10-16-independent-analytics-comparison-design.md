## เป้าหมายและขอบเขต

ผู้ใช้เลือกวันและเวลาของช่วงหลักกับชุดเทียบต่างกันทั้งหมดได้ โดยระบบเก็บแต่ละชุดอย่างอิสระ แสดงยอดจริงและหน่วยให้ชัดเจน แยกกราฟเมื่อหน่วยต่างกัน และงด % เมื่อเทียบกันไม่ได้ ใช้ picker, Calendar, Select, Button, Popover และกราฟเดิม คง controls สูง 32 CSS px และลูกศร/ปุ่มไอคอน 32 × 32 CSS px

งานนี้อยู่ใน Dashboard widget และหน้ารายละเอียดสถิติเครื่องมือเดียวกัน จึงไม่ใช้ House Workspace Shell ไม่เปลี่ยน booking picker หรือ house workspace ไม่เพิ่ม dependency ไม่แก้ API/SQL ของ baan-pool-villa และไม่เพิ่มการเรียก API ต่อวัน

## ปัญหาปัจจุบันที่ยืนยันได้

- `websitePeriodChange` งด % สำหรับหลายวันที่ clocks ต่างกัน แต่วันเดียวที่ clocks ต่างกันและระยะเวลาเท่ากันยังคำนวณ % เช่น 09–12 เทียบ 18–21
- การตัดสินหน่วยและคำเตือนกระจายใน series, graph, summary และ detail บางจุดเดาจากวันที่/time fields จึงเสี่ยงไม่ตรงกับรายงานจริง
- กราฟเทียบจับคู่ตามลำดับ ทำให้ชั่วโมงคนละเวลาถูกวางทับกันได้ แม้ tooltip แสดงเวลาจริง
- ชุดเทียบที่เพิ่มถูกเก็บเป็นช่วงตายตัว ต้องสื่อว่าเป็นชุดอิสระ ไม่มีสถานะอัตโนมัติที่ซ่อนอยู่

## ตัวเลือกและเหตุผล

1. บังคับวัน/เวลาเหมือนกัน: ตรวจง่าย แต่ไม่รองรับการสำรวจเงื่อนไขต่างกันตามที่ต้องการ
2. **เลือกอิสระ + กติกากลาง + แยกกราฟตามความเข้ากันได้ (เลือกแนวทางนี้):** ใช้ข้อมูล/API และ component เดิม แสดงข้อจำกัดทันที
3. รวมทุกกรณีเป็นรายวันหรือหารเป็นค่าเฉลี่ย: สูญรายละเอียดรายชั่วโมงหรือเพิ่มสมมติฐานทางสถิติ จึงยังไม่เพิ่ม

## หน้าจอและการเปลี่ยนสถานะ

ช่วงหลักและชุดเทียบอยู่แถวเดียวกันและแนวระดับเดียวกันบน desktop ใต้หัวการ์ด บนมือถือเรียงสองแถว ชุดเทียบมี label “ชุดเทียบ” พร้อม picker ของตัวเองและปุ่มเอาออก ปุ่ม “ใช้จำนวนวันและเวลาตามช่วงหลัก” อยู่ใต้ปฏิทินภายใน popup ของชุดเทียบ

- กดเพิ่มชุดเทียบ: เริ่มด้วยช่วงก่อนหน้าจำนวนวันเท่ากันและ clocks เดียวกัน จากนั้นทั้งสองชุดเป็นอิสระ การเปลี่ยนช่วงหลักไม่เปลี่ยนวัน/เวลา/สถานะระบุเวลาของชุดเทียบ
- ทั้งสอง popup มี “ระบุช่วงเวลา” ใต้ปฏิทิน ปิด = เต็มวัน 00:00–24:00 เปิด = เลือกทีละชั่วโมง เริ่ม 00–23 สิ้นสุด 01–24 และเริ่มต้องน้อยกว่าสิ้นสุด ไม่รองรับข้ามคืน
- วันที่และเวลาเป็น draft จนกด “ใช้” ครั้งเดียว; cancel/Escape/outside ทิ้ง draft ทั้งชุด เปิดใหม่ใช้ค่าที่ commit ล่าสุด ไม่ยิง API ระหว่าง draft
- ปุ่มปรับเงื่อนไข: ยึดวันสิ้นสุดใน draft ของชุดเทียบเป็นวันสิ้นสุด คำนวณ `comparison.from = comparison.to - (จำนวนวันหลัก - 1)` และคัดลอก clocks หลักที่ normalize แล้ว ไม่คัดลอกวันที่หลัก ไม่เปลี่ยนรายชื่อเว็บไซต์
- ปุ่มปรับจำนวนวันและเวลาแก้เฉพาะ draft จากนั้นกด “ใช้” เพื่อโหลดช่วงใหม่ เป็นการเปลี่ยนเงื่อนไขที่ระบุชัด ไม่เปิดการติดตามอัตโนมัติ หากผลวันเริ่มก่อน 1900-01-01 ให้ปิดปุ่มพร้อมเหตุผล ห้าม clamp หรือเลื่อนช่วงโดยเงียบ
- กรณีเดือน implicit มีเพียงวันเดียวและยังใช้ source 1.0/day ให้ปิดปุ่มปรับเงื่อนไขพร้อมคำอธิบาย “เลือกช่วงหลักจากปฏิทินก่อนปรับเงื่อนไข” เพื่อไม่แอบเปลี่ยนหน่วยของช่วงหลัก; ผู้ใช้ยังแก้ชุดเทียบอิสระและดูแยกกราฟได้
- เอาชุดเทียบออกลบเฉพาะ comparison; วัน เวลา เว็บไซต์ และมุมมองหลักคงเดิม
- ระหว่าง pending ปิด actions ที่ก่อ navigation ซ้ำ มีข้อความโหลด และไม่แสดงข้อมูลเก่าราวกับเป็นเงื่อนไขใหม่ ใช้ loading state ที่มีอยู่
- หลัง load แสดงเหตุผลที่งด % ใกล้ชุดเทียบและใน summary/detail ด้วยข้อความเดียวกัน ไม่ซ่อนไว้ใน tooltip เท่านั้น

## ประเภทและกรณีการเลือก

S24 = วันเดียวเต็มวัน, ST = วันเดียวระบุเวลา, R24 = หลายวันเต็มวัน, RT = หลายวันใช้ช่วงเวลาเดียวกันทุกวัน เต็มวัน normalize เป็น 00:00–24:00 เสมอ การเปิดตัวเลือกแต่ยังคง 00–24 ให้ผลเชิงข้อมูลเท่ากับเต็มวัน

| คู่เงื่อนไข (สลับหลัก/เทียบได้) | กราฟแนวโน้ม | % เมื่อข้อมูลครบและสิ้นสุดแล้ว |
| --- | --- | --- |
| S24 / S24 | ซ้อนรายชั่วโมง | ได้ |
| ST / ST | clocks ตรงกันซ้อน; ต่างกันแยก | ได้เมื่อ clocks ตรงกัน |
| S24 / ST | แยกรายชั่วโมง | งด หาก ST แคบกว่าเต็มวัน |
| R24 / R24 | ซ้อนรายวันตามลำดับวัน | ได้เมื่อจำนวนวันเท่ากัน |
| RT / RT | ซ้อนรายวัน พร้อม clocks ทั้งสองชุด | ได้เมื่อจำนวนวันและ clocks ตรงกัน |
| R24 / RT | ซ้อนรายวัน พร้อมคำเตือนช่วงเวลาต่างกัน | งด หาก RT แคบกว่าเต็มวัน |
| S24 / R24 | แยกรายชั่วโมง/รายวัน | งด |
| S24 / RT | แยกรายชั่วโมง/รายวัน | งด |
| ST / R24 | แยกรายชั่วโมง/รายวัน | งด |
| ST / RT | แยกรายชั่วโมง/รายวัน | งด |

กรณี S/R เป็น explicit picker selection ส่วน URL เดิมที่เป็นรายงานเดือน implicit ใช้หน่วยจาก `AnalyticsPeriod.contract_version` จริง: 1.1 = hour; 1.0/1.2 = day เดือนที่เพิ่งเริ่มและมีเพียงวันเดียวยังคง daily ของ 1.0 ห้ามอ้างว่ามี hourly เมื่อ source ไม่ได้ส่งมา เมื่อผู้ใช้ยืนยันวันเดียวจาก picker จึงเป็น 1.1 ตามเดิม

## กติกากลางในการแสดงผล

แยกการตัดสิน layout ออกจากการคำนวณ % โดย layout ขึ้นกับหน่วย/เงื่อนไขที่เลือก ไม่ขึ้นกับเว็บไซต์แรกที่โหลดได้

- หน่วยต่างกัน → แยกกราฟ โดยแต่ละกราฟระบุช่วง วัน เวลา และหน่วยของตัวเอง
- หน่วย hour ทั้งคู่แต่ clocks ต่างกัน → แยกกราฟ ไม่จับ 09:00 กับ 18:00 เป็นจุดเดียว
- หน่วย hour ทั้งคู่ clocks เดียวกัน → ซ้อนกราฟ แกนแสดงชั่วโมงจริง Tooltip แสดงวันจริงทั้งสองชุด
- หน่วย day ทั้งคู่ → ซ้อนกราฟตาม “วันที่ 1, วันที่ 2…” แม้จำนวนวันต่างกัน Tooltip แสดงวันและ clocks จริงแต่ละฝั่ง กราฟยาวตามจำนวนวันที่เลือกมากกว่า
- จุดนอกช่วง ไม่มีข้อมูล หรือก่อน retention ใช้ `null/—`; observed zero ใช้ 0 ห้ามเติม 0 หรือเชื่อมเส้นข้ามช่องว่าง เว็บไซต์แรกโหลดไม่ได้ต้องไม่ทำให้แกนหรือเว็บที่สำเร็จหาย
- การซ่อนเว็บไซต์มีผลทั้งสองชุดพร้อมกัน สีเว็บไซต์คงเดิม ไม่แก้ยอดต้นทาง/เงื่อนไข URL
- มุมมองยอดรวมแสดงยอดของแต่ละชุดพร้อมเงื่อนไข/ระยะเวลาที่เลือก แม้ layout แนวโน้มต้องแยก ไม่สรุปว่าดีขึ้น/แย่ลงเมื่อเทียบไม่ได้

อนุญาต % เฉพาะเว็บไซต์ที่อยู่ทั้งสองชุด หน่วยเดียวกัน จำนวนวันเท่ากัน clocks ที่ normalize แล้วตรงกัน ข้อมูลครบ และทั้งสองช่วงสิ้นสุดแล้ว ทุกข้อบังคับใช้กับ hour/day เหมือนกัน ช่วงวันที่ซ้อนทับหรือเหมือนกันอนุญาตได้และแสดงวันที่จริง; ช่วงเดียวกัน/เงื่อนไขเดียวกันได้ 0% เมื่อฐานไม่เป็นศูนย์

เหตุผลเรียงลำดับคงที่และอาจมีหลายข้อ: “เว็บไซต์ไม่อยู่ในทั้งสองชุด”, “หน่วยเวลาต่างกัน”, “จำนวนวันต่างกัน”, “ช่วงเวลารายวันต่างกัน”, “โหลดไม่ได้”, “ข้อมูลไม่ครบ”, “ยังไม่ถึงช่วงเวลา”, “ยังไม่สิ้นสุดช่วงเวลา” แสดงเหตุผลโครงสร้างในส่วนกราฟ และเหตุผลข้อมูลแยกตามเว็บไซต์ ห้ามใช้จำนวน sites ที่โหลดล้มเหลวเป็นจำนวน sites ที่เงื่อนไขต่างกัน

ฐานเทียบ 0 → หลัก >0 แสดง “เพิ่ม X ครั้งจากฐาน 0” ไม่หารด้วยศูนย์; 0 → 0 แสดง “ไม่เปลี่ยนแปลง (0 → 0)” ยอดจริงอาจมีค่าได้แม้ coverage ไม่ครบ ต้องระบุ “ยอดเท่าที่มีข้อมูล” และงด % ไม่ปิดบังยอด

ระยะเวลาที่แสดงเป็นระยะเวลาที่ร้องขอ: วันแบบ inclusive × ชั่วโมงต่อวัน ไม่ใช่จำนวนชั่วโมงที่สังเกตแล้ว สำหรับช่วง ongoing/future/retention แสดงสถานะและ `as_of` แยก ห้ามใช้เวลา requested ไปทำค่าเฉลี่ยโดยอัตโนมัติ

## Architecture และสัญญาภายใน

- เพิ่ม `lib/website-analytics-comparison-policy.ts` เป็น pure functions สำหรับ normalize/describe, เลือก layout, ตรวจ compatibility/reasons และปรับเงื่อนไขชุดเทียบ ไม่มี React/router/fetch
- หน่วยต้องมี provenance จาก source period: เพิ่ม `analyticsPeriodGranularity(period): 'hour'|'day'` ใน `lib/website-analytics.ts`; ส่งหน่วยของทั้งสองชุดจาก service/loader ไป series/chart เป็น explicit prop ไม่เดาจากจำนวนวัน หรือจำนวน rows ของเว็บไซต์แรก
- `WebsitePreviousPeriod` เพิ่ม `granularity: 'hour'|'day'`; `websitePeriodSeries` รับหน่วย explicit เป็น argument ท้าย, อัปเดต callers และ fixtures ทั้งหมด `WebsiteSiteSummary`, graph และ trend รับหน่วยจากเจ้าของ report ด้วย
- `websitePeriodChange` ใช้ assessment กลางก่อนคำนวณเดิม Components ไม่คัดลอก if/else business rules ใหม่ ใช้ label mapping กลางใน `period-comparison-summary.tsx`
- ใช้ `AnalyticsDateRange`, `WebsiteScopeSelection`, `WebsiteDatasetSelection` และ URL รูปเดิมต่อ ไม่มี field auto-mode ใหม่ scope เดิมไม่มี clocks ให้ normalize สำหรับการเทียบเป็นเต็มวัน โดยไม่เปลี่ยน API contract ของ implicit month
- ขอบเขตภายนอกยัง validate dates, paired clocks, future dates และ site allowlist ตามเดิม; producer contracts 1.0/1.1/1.2 ไม่เปลี่ยน Snapshot ทั้งสองชุดเดียวกัน chunk 90 วัน concurrency สูงสุด 2 และ secret server-only
- อ่านผ่าน service เดิม ไม่ยิง report ต่อวันเพื่อทำกราฟเทียบ ไม่เพิ่ม dependency หรือ migration
